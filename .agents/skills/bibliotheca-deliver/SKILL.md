# Develop and deliver Bibliotheca issues

1. Read [AGENTS.md](../../../AGENTS.md) and the [agent guide](../../../docs/agent-guide.md). Use [bibliotheca-issues](../bibliotheca-issues/SKILL.md) to retrieve the live issue, comments, dependencies and acceptance criteria with gh. Verify that the issue is open and check the branch, remote and working tree. Preserve existing edits. For an epic with independent children, confirm the first child unless the user already specified the scope.
2. Choose and explain the model and reasoning effort based on risk. Use a fast model with low or medium effort for isolated changes, a general coding model with medium or high effort for broader changes, and the strongest available model with high effort for architecture, authentication, migrations or concurrency. Respect the user's model choice and disclose material availability constraints. Delegate only when available and authorized.
3. When GitHub updates are authorized, inspect the issue's GitHub Projects memberships and configured Status options. Set the appropriate existing in-progress status if the issue belongs to an applicable project. Use the project and item IDs and the existing field and option IDs with `gh project item-edit`. Where no applicable status field exists, track progress through the issue report and its Open or Closed state.
4. Before implementing, read the repository skills for each affected layer and apply their guidance to the implementation and review.
   - For ASP.NET Core API changes, start with [dotnet-webapi](../dotnet-webapi/SKILL.md). Add focused .NET skills where relevant, such as [optimizing-ef-core-queries](../optimizing-ef-core-queries/SKILL.md) for EF Core queries or [run-tests](../run-tests/SKILL.md) for backend validation.
   - For Vue PWA changes, start with [vue-best-practices](../vue-best-practices/SKILL.md). Use [Vue Router](../vue-router-best-practices/SKILL.md), [Pinia](../vue-pinia-best-practices/SKILL.md) and [Vue testing](../vue-testing-best-practices/SKILL.md) when the change touches routing, stores or frontend tests, respectively.
   - When an issue spans both layers, apply both sets of guidance and verify the API contract through the affected frontend flow.
   Implement through normal entry points. Cover acceptance criteria with appropriate unit and integration tests, and add regression coverage where existing tests leave a gap. Include browser or end-to-end checks when the change affects the PWA or a browser flow. Run the applicable commands from the agent guide, record results and distinguish fixture-based checks from live external validation.
5. Review the diff and verify tests and staged changes before any authorized commit. Publish the intended work to the established remote using the repository's delivery workflow when authorized. Verify the published result before closing the issue.
6. For authorized GitHub delivery, post a report on the issue with `gh issue comment NUMBER --repo labsilva/bibliotheca --body-file PATH`. Include what changed, tests and results, links to published work and any outstanding criteria or validation. Once all acceptance criteria are met and the work is published, set the applicable existing completed project status, close the issue using `gh issue close NUMBER --repo labsilva/bibliotheca --reason completed`, and verify the issue state and any project status remotely. On retry, check existing comments and state before repeating updates. If delivery is blocked, report the blocker and leave the issue open.
7. Summarize implementation, validation, publication and verified issue state to the user. Apply GitHub mutations, commit and push only within the scope authorized by the user's request.
